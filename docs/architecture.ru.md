# Проект архитектуры OpenWrt VPN Manager
Дата: 11 октября 2026. Целевая архитектура; локальная реализация прототипа и её ограничения описаны в prototype.ru.md. Проверка на целевом роутере не выполнена.



## 1. Компоненты

1. OpenWrt daemon под procd: discovery, ограниченная очередь probes, расчёт политик, журнал, транзакции и API. Предпочтительно ucode; окончательно подтвердить прототипом на целевом SDK.
2. Podkop adapter: чтение UCI и созданной Podkop конфигурации; разрешённая разница — interface только выбранных section с connection_type=vpn. Безопасный apply требует отдельного подтверждённого механизма; текущий reload ему не соответствует.
3. HTTPS JSON-RPC gateway uhttpd → ubus: rpcd login, отдельная группа ACL, объект vpn.controller. Не включать ubus_noauth. Локальный daemon регистрирует объект; rpcd отвечает за удалённую сессию и разрешения. ACL RPC не заменяет модель прав локального сокета ubus.
4. HA custom integration openwrt_vpn_manager: собственный асинхронный клиент, общий coordinator на config entry, UI-настройка, сущности и события. Без SSH в цикле работы.

Разрешённые процедуры вызываются фиксированными программами с argv. Запрет shell -c/eval и конкатенации пользовательских аргументов. Существующие curl/jq могут быть использованы после проверки возможностей; установка новых зависимостей на целевом роутере сейчас не выполняется.

## 2. Данные и идентичность

| Объект | Поля и смысл |
|---|---|
| Controller | controller_id (устойчивый локальный UUID), boot_id, api_version, policy_revision, config_revision, snapshot_seq, run_mode, automation_enabled |
| Capability | supported, verified, reason; отдельно discovery, probes, section_probe, safe_apply, fail_closed |
| VPN | vpn_id, network_id, device_name, kind, user_approved, health, last_observed_at, metrics |
| Section | реальный UCI section_id, connection_type, desired_policy, configured_vpn, observed_runtime_vpn, apply_state, last_change |
| Policy | manual/auto, manual_vpn_id либо candidates с приоритетами, priority/quality, return_policy, thresholds, section_targets |
| Observation | endpoint_id, protocol, device, address_family, outcome, latency_ms, external_ip, evidence_level, checked_at |
| Operation | operation_id, request_id, payload_hash, revisions, phase, outcome, changed_fields, deadline |
| Event | устойчивый event_id, cursor, timestamp, section_id/vpn_id, type, reason, operation_id |

Не смешивать настроенный интерфейс, прочитанный bind_interface и подтверждённый трафиком VPN. Подтверждённый внешний IP имеет время, семейство IP и источник доказательства; при недоступной проверке значение unknown, не фиктивный адрес.

Секции обнаруживаются повторно. Rename/delete прекращает применение старой политики и создаёт событие; перенос по одному совпадению имени/содержимого не выполняется. Преобразование vpn→proxy/block/exclusion немедленно исключает секцию из управления.

inbound_vpn и устройства, составляющие LAN/WAN/управляющий путь, не могут стать кандидатами. Известные vpn_a/vpn_b/vpn_c — начальные обнаруживаемые элементы, не предел архитектуры. Пользователь подтверждает пул; вывод list/discovery сам по себе не даёт разрешения на запись.

## 3. Состояния и политика

run_mode=observe по умолчанию; automation_enabled=false. В observe разрешены чтение, проверки, сохранение желаемых политик и показ предложений, но не изменение Podkop. Переход в control — явная настройка UI после проверки возможностей безопасного применения. Глобальный switch управляет только автоматическими решениями; не останавливает Podkop, VPN или probes.

Состояние VPN: unknown → healthy/degraded → unavailable. Исчезнувший device — missing. Состояние stale не приравнивается к подтверждённому отказу. ICMP unsupported не штрафует VPN как неработающий.

Значения из ТЗ: цикл 60 секунд, не менее 3 независимых ресурсов, минимум 2 успешных проверки, 3 последовательных неуспешных цикла для отказа, удержание 600 секунд. Предлагаемая интерпретация кворума: минимум 2 независимых успешных endpoint в цикле; отдельные обязательные ресурсы секции проверяются дополнительно. Все пороги настраиваются, схема не допускает невозможного кворума.

Priority: первый здоровый разрешённый кандидат. Возврат на более приоритетный — по return_policy с учётом удержания. Конкретные варианты возврата: sticky или after_hold. Quality: сравнение здоровых кандидатов по взвешенным HTTP/TCP-успехам, задержке и стабильности окна; ICMP входит только при наличии данных. Минимальное улучшение и число подтверждений задаются отдельно. Формулу, нормализацию и тестовые наборы зафиксировать до реализации алгоритма, без постоянных speedtest.

Подтверждённый отказ текущего VPN допускает аварийный переход до завершения удержания; удержание защищает от косметических переключений и возвратов. Manual сохраняется при любых отказах: без самовольной смены, с аварийным состоянием и продолжением probes.

Если все кандидаты unavailable: последнее назначение остаётся, новых назначений на нерабочий VPN и WAN нет; секция degraded/all_unavailable, одно событие на переход. Это поведение политики; гарантия блокировки утечек требует отдельного доказанного data-plane механизма.

Отключение автоматики отменяет ещё не применённые автоматические планы. Уже записанная операция доводится до проверки/отката локально; потеря HA не бросает её посередине.

## 4. RPC v1

Все методы имеют строгие схемы и ограниченные размеры. Большие результаты страницами. Секреты, полные UCI-конфигурации и сырые shell-логи не возвращаются.

| Метод | Содержание |
|---|---|
| capabilities | Идентичность, версия API, ограничения и причины неподдержанных функций |
| status | Агрегированный snapshot, ревизии, свежесть, состояния служб и операций |
| sections | Обнаруженные VPN-секции и их политики |
| vpns | Разрешённый discovery/метрики исходящих VPN |
| history | cursor, limit, необязательный section_id |
| operation | Итог/прогресс по operation_id либо request_id |
| set_automation | enabled; управляет глобальной автоматикой |
| configure | Разрешённые настройки контроллера: run_mode, probes, thresholds, retention, утверждённый пул |
| set_policy | section_id, manual/auto, candidates, algorithm, return_policy и пороги |
| assign_vpn | Узкая удобная операция ручного выбора section_id/vpn_id или возврата в Auto |
| diagnose | Фиксированный профиль и существующий vpn_id/section_id, без произвольной команды |

Изменения содержат request_id, expected_policy_revision и ожидаемый config_revision при затрагивании Podkop. Запрос устаревшей конфигурации отклоняется. Одновременные изменения объединяются в один план применения за цикл.

request_id дедуплицируется устойчиво, один id с разным payload отклоняется. Клиент после потери ответа делает operation(request_id), не запускает новую мутацию. HTTP success и ubus result=[0,...] не подменяют operation outcome.

Новая ACL расширяет проект из транспортного документа только перечисленными методами: read — capabilities/status/sections/vpns/history/operation; write — set_automation/configure/set_policy/assign_vpn/diagnose. Общие uci/file/rc/service/network/system права HA отсутствуют. Обслуживание собственной RPC-сессии проверить на реальном rpcd; не давать список чужих сессий.

В configure не разрешать произвольные пути/службы. Настройка проверочных ресурсов требует отдельной схемы: только HTTP/HTTPS, запрещены credentials в URL, редиректы в локальную/служебную сеть, link-local/metadata и иные схемы. Endpoint-адреса проверяются перед запросом; диагностический API не превращается в удалённый сетевой сканер.

## 5. Транзакция и LuCI

Операция: validated → prepared → applied → verifying → succeeded; при ошибке rolling_back → rolled_back либо recovery_required. Отказ до изменения имеет исход failed. Observe возвращает proposed с объяснением, а не succeeded.

До изменения:
- Проверить run_mode, capabilities, разрешённые VPN, кворум, защищённые ресурсы и доступность административного пути.
- Считать весь актуальный Podkop и хеш; отдельно сохранить изменяемые interface. Проверить внешние staged changes.
- Сгенерировать и проверить будущую конфигурацию штатным безопасным render-механизмом. Такого публичного механизма в исследованном Podkop пока нет.
- Устойчиво записать журнал операции и снимок собственных полей, затем повторно проверить revisions.

Один локальный lock сериализует daemon. LuCI его не использует: сравнение конфигурации обязательно, но без координации writers остаётся гонка между проверкой и записью. Полное решение потребует проверенного способа сериализации на границе UCI/Podkop. Этот риск нельзя скрывать словом «транзакция».

При откате восстанавливать только собственные изменённые поля, если их текущие значения ещё соответствуют применённым нами. Чужие изменения не перетирать; конфликт переводит операцию в recovery_required. После crash восстановить журнал до новых записей. Таймаут применения и rollback работает на роутере, без участия HA.

Не восстанавливать весь пакет из старой копии поверх правок LuCI. Не редактировать JSON sing-box вручную. Не добавлять firewall guard в рабочую сеть без отдельного разрешения. Защита перед/во время apply и поведение при power loss должны быть испытаны на стенде; rollback после утечки её не отменяет.

## 6. Сущности HA и история

На config entry — runtime_data с клиентом, coordinator и event cursor. unique_id включает controller_id плюс стабильный id ресурса; адрес и отображаемое имя не служат идентификатором. Идентичный controller_id не подключается повторно.

Платформы: switch (глобальная автоматика), select (Auto/доступные VPN по секции), sensor/binary_sensor (все состояния и метрики из ТЗ), button (диагностика). Метрики handshake для протокола без handshake показываются как unsupported. Последний внешний IP не объявляется свежим после потери связи.

Config Flow: HTTPS endpoint, RPC login, доверие CA, проверка сертификата, возможностей и controller_id; ConfigEntryAuthFailed для учётных данных, ConfigEntryNotReady для временной недоступности. Options Flow: политики секций, алгоритмы, кандидаты, пороги, run_mode и интервалы. Настройки политики сохраняются на роутере, HA не является их единственным хранилищем.

Изначально local_poll: агрегированный status + история с cursor. Push/SSE не обязателен для автономности. После записи — свежий status, без оптимистического объявления успеха.

События HA содержат event_id, controller_id, тип и контекст без секретов. Устойчивый cursor исключает повторную выдачу всей истории при рестарте; детектировать разрыв истории после retention. Потеря связи создаёт одно событие на переход, восстановление — отдельное. Периодическое polling не создаёт уведомление каждую минуту.

Пример Lovelace использует стандартные карточки и три известных VPN как пример, а не ограничение discovery. Русская/английская локализации обязательны. Для прототипа минимальная версия ограничена проверенной Core 2026.10.1; более ранние версии не испытаны.

## 7. Хранение, стенд и последовательность разработки

Настройки контроллера — отдельный UCI-пакет, права доступа ограничены. События и метрики — ограниченный кольцевой журнал с пакетной записью; не писать на flash каждый probe. Журнал транзакций и дедупликация мутаций сохраняются устойчиво до ответа о принятии операции; объём, срок хранения и поведение после исчерпания диска тестируются.

Порядок:
1. Runtime-прототип ucode и локальная среда Linux/OpenWrt.
2. Чистая модель политик/состояний и сценарии трёх VPN, без реального сетевого изменения.
3. Discovery, VPN probes, история, observe RPC с отрицательными ACL-тестами.
4. HA Config/Options Flow и полный набор сущностей на моделируемом контроллере.
5. Стендовый Podkop apply/rollback и проверка реального маршрута секций, включая все отказы и защиту inbound_vpn.
6. Воспроизводимые пакеты, HACS, обновление, удаление и пошаговое внедрение только после отдельного разрешения.

Локально создан Python-симулятор модели контроллера и HA-интеграция: см. prototype.ru.md. Интеграция проверена на Core 2026.10.1 с локальным HTTPS-симулятором. Нативный runtime ucode/procd и OpenWrt-стенд ещё не созданы; safe_apply и fail_closed для настоящей сети не доказаны.
