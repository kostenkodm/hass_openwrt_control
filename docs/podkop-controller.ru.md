# Нативный прототип управления Podkop — 0.2.0

## Что реализовано

Home Assistant обращается к `vpn.controller` через HTTPS ubus JSON-RPC. Нативная служба ucode/procd обнаруживает существующие секции `connection_type=vpn` и интерфейсы WireGuard/AmneziaWG. Только локально одобренные исходящие интерфейсы становятся кандидатами. Защищённые и исходные интерфейсы задаются локально и исключаются из кандидатов. HA не получает UCI, shell, service, rc, system или network API.

Для каждой секции сохраняются Manual/Auto, кандидаты, приоритет/качество, время удержания, порог качества и политика возврата. При полном отказе назначение сохраняется, тревога возникает один раз за переход. После отката повторное применение блокируется, в том числе после перезапуска, до новой команды политики. HA может быть выключен: worker продолжает пробы и выбор.

Начальные значения: observe, автоматика выключена, пробы 60 с, три ресурса, quorum 2, три неудачных цикла, удержание 600 с. Ручные назначения и настройки хранятся на роутере с fsync и атомарным переименованием. История ограничена 200 событиями, операции — 256 записями. Старые request_id после этого окна нельзя повторять.

## Настоящее применение

1. Проверяются версия и SHA-256 всех используемых файлов Podkop 0.7.23, локальные разрешения, существующий перехват IPv4 и маршрутизация метки Podkop.
2. Создаётся durable-журнал с request_id и назначениями до/после. Сохраняются контрольные копии UCI, конфигурации sing-box и защищённых network/firewall/dhcp.
3. Изолированный UCI cursor меняет только `interface` существующих VPN-секций в staging-каталоге.
4. Адаптер загружает функции установленного Podkop без CLI-dispatch и вызывает его штатный генератор. Запись rule sets и изменение nft подавлены; недостающий rule set вызывает отказ. Бинарная конфигурация sing-box не правится вручную.
5. Структурное сравнение допускает только нужные VPN-привязки и диагностические mixed-inbound на loopback. Любое другое отличие — отказ.
6. `sing-box check`, сравнение ожидаемых файлов, атомарная установка UCI и runtime-конфигурации, затем только `/etc/init.d/sing-box reload`. `podkop reload/restart`, переключение назначения не перезапускает интерфейсы или сеть.
7. Проверяются UCI, runtime bind_interface, procd и HTTPS через loopback-inbound конкретной секции. Ожидаемый внешний IP должен принадлежать локально заданному списку VPN.
8. При ошибке восстанавливаются только ещё принадлежащие операции interface-поля; чужие UCI-поля сохраняются. Чужая runtime-конфигурация не перезаписывается. Неподтверждённый откат или конфликт приводит к recovery_required и останавливает дальнейшие записи.

Диагностические inbound слушают только 127.0.0.1, порты от 23000 в порядке section_id. Они создаются штатной функцией Podkop. Пробы кандидатов используют curl с привязкой к устройству, фиксированным адресом --resolve, проверкой TLS и без redirect. Произвольные URL через RPC не принимаются. Требуется совпадение имени UCI-интерфейса и kernel device, иначе кандидат не считается доступным.

## Честные границы безопасности

Это **экспериментальный контроллер**, не пройденная production-приёмка. `production_control=false`, `safe_apply=false`, `fail_closed_verified=false`. Для стендового режима есть отдельное `experimental_control`, вычисляемое по локальным условиям.

Podkop 0.7.23 исследован для IPv4. Управление отказывается включаться, если IPv6 all/default не выключен. Контроллер сам не меняет sysctl или firewall. Не выключайте IPv6 на рабочем роутере ради этого прототипа без отдельной оценки влияния на его сеть и inbound_vpn.

libuci блокирует inode файла и заменяет файл через rename. У писателя, уже открывшего старый inode, остаётся узкая гонка с другим commit. Сравнение файлов и обнаружение изменений LuCI покрывают обычные конфликты, но не доказывают сериализацию всех несогласованных писателей. Поэтому `exclusive_podkop_writer=false` по умолчанию; для экспериментального включения требуется отдельное контролируемое окно без параллельных изменений Podkop. Полное автоматическое согласование LuCI и обновления списков остаётся условием production-приёмки.

Нативные тесты используют настоящий OpenWrt rootfs x86_64, Podkop и sing-box, но VPN-устройства представлены изолированными veth. Это проверяет bind_interface, применение, ACL, TLS и заданные IPv4-потоки; не подтверждает драйвер AWG, аппаратные offload-пути, все UDP-сценарии и защиту IPv6 на целевом роутере.

## Кнопки перезапуска VPN

HA создаёт кнопку «Перезапустить …» для каждого одобренного исходящего VPN. По умолчанию она недоступна. На OpenWrt необходимо локально задать `restart_enabled=true` и `restartable_interfaces` с разрешёнными именами; экспериментальные проверки `ready` также должны пройти, а режим работы должен быть `control`. В `observe` реальный перезапуск запрещён. HA не может изменять эти списки. После изменения локального config.json требуется перезапустить контроллер и перезагрузить интеграцию HA для обновления возможностей. Входящие, исходные для Podkop, LAN/WAN и управляющие интерфейсы исключаются.

Кнопка вызывает только `vpn.controller.restart_vpn` с vpn, request_id и expected_revision. Контроллер сериализует запрос, сохраняет журнал, выполняет down/up только указанного netifd-интерфейса и проверяет его состояние и действительный HTTPS-выход с ожидаемым IP. Текущие соединения через этот VPN будут прерваны. Политики и назначения секций команда не меняет; после её завершения автономная автоматика продолжает обычную работу.

Повтор того же request_id возвращает прежний результат. После сбоя между down/up восстановление допускает только up, повторный down не выполняется. Неподтверждённое восстановление блокирует дальнейшие команды (`recovery_required`). Права HA на `network.interface.*`, UCI, shell или управление другими службами не добавляются. В демонстрации кнопки создают только события с `simulated=true`.

## Установка и подключение HA

Пакет OpenWrt и интеграция HA устанавливаются отдельно. Установка пакета не включает службу и не меняет настройки Podkop. Не выполняйте команды ниже на целевом роутере до отдельного разрешения на production-деплой и сверки резервной копии.

1. Проверить архитектуру, версию Podkop, sing-box, пути и SHA-256. Приложенный пакет собран для aarch64_cortex-a53, OpenWrt 25.12.5 (SDK mediatek/mt7622); совместимость с конкретным роутером нужно проверить до установки.
2. Установить проверенный пакет через apk. Сначала оставить `/etc/vpn-controller/config.json` с control_enabled=false.
3. Подготовить отдельный доступ локально: `python tools/prepare_router_access.py --hostname router.lan --lan-ip <LAN_IP> --output work/router-access`. Нужны cryptography и OpenSSL. Пароль не печатается и не передаётся в argv.
4. Проверить `rpcd.fragment` и `uhttpd.fragment`, затем добавить их в соответствующие конфигурации. Скопировать server.pem/server.key в `/etc/vpn-controller/tls`, ключ 0600. ACL из пакета предоставляет только методы vpn.controller. Unix/SSH-учётная запись не создаётся.
5. HTTPS слушает только указанный LAN IPv4, порт 8443; HTTP-listener не создаётся. Проверить отсутствие WAN-listener, WAN-разрешений и DNAT/port forwarding. Настройка не открывает firewall. Учитывать отдельный сегмент HA, если он используется.
6. В локальном config.json задать protected_interfaces (входящий VPN и управляющий путь), source_interfaces (источники перехвата Podkop), одобренные VPN, ожидаемые внешние IPv4, минимум три ресурса разных операторов. Каждый ресурс содержит host, фиксированный IPv4 ip, scheme, port, path, egress. Ресурсы с egress=true требуют HTTPS и текстовый ответ, содержащий только IP. Для секций можно задать отдельные resources. Не используйте placeholder IP из примеров.
7. Пакет содержит шаблон `/usr/share/vpn-controller/vpn-controller.init`, а не активный init-скрипт. После отдельного разрешения скопировать шаблон в `/etc/init.d/vpn-controller`, установить режим 0755 и запустить службу. В HA добавить интеграцию → «Подключение к контроллеру», HTTPS endpoint, логин/пароль из ha-connection.json, содержимое ca.pem. Проверка CA и имени сервера обязательна.
8. В observe проверить реальные секции и доступность. Выбор VPN меняет желаемую политику; применённое назначение показывается отдельным сенсором. Для экспериментального control нужна локальная активация, проверки guard и подтверждённое окно единственного писателя; по умолчанию это запрещено.

Сертификат профиля действует 365 дней. CA private key не сохраняется; для обновления этого прототипного профиля нужно выпустить новую CA и обновить доверие HA. Никакие файлы из work/router-access нельзя коммитить или публиковать.

## Сборка и тестирование

`python tools/fetch_native_dependencies.py --sdk --sources` загружает закреплённые зависимости в ignored work (для SDK после проверки SHA256 распаковать tar.zst в work/openwrt-sdk). Нужны Linux/WSL, gcc, cmake, make, pkg-config, libjson-c-dev, libssl-dev, jq, curl, ip-full, nftables, util-linux, OpenSSL и Python. Для HTTPS-клиента нужен ранее созданный `work/venv-linux`.

`tools/bootstrap_native.sh` собирает нативные библиотеки для быстрых unit-тестов ucode. `sudo bash tools/run_native_tests.sh` запускает core-тесты и изолированный rootfs-стенд. Сторонние GPL-файлы загружаются только в ignored work и не входят в MIT-пакет. `tools/build_openwrt_package.sh` собирает небольшой пакет компилятором и apk-tools официального SDK; полный SDK make на нечувствительном к регистру диске Windows не используется. Пакет unsigned, без postinst и автозапуска. Проверять пакет можно локально, установка на роутер этим скриптом не выполняется.

Подробный результат запуска сохраняется в `outputs/podkop-0.2.0/TEST-REPORT.md`. Первоначальное ТЗ и его дополнительные требования сохраняются: этот документ не отменяет незавершённые условия приёмки.
