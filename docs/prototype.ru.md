# Прототип HA-интеграции 0.1.0

Этот документ описывает демонстрацию версии 0.1.0. Актуальная установка 0.2.0 описана в [README](../README.md), нативный контроллер — в [отдельной инструкции](podkop-controller.ru.md). Установка в действующий HA выполняется владельцем самостоятельно.

## Встроенная демонстрация

После установки добавьте интеграцию и выберите «Демонстрационный режим». Ввод URL, сертификата и пароля не требуется. Устройство **OpenWrt VPN — Demo** содержит 52 сущности пяти платформ: sensor, binary_sensor, select, switch, button. Все состояния имеют `simulated=true`.

Три синтетические секции: `main`, `media`, `custom`. Исходные ручные назначения: vpn_a, vpn_b, vpn_c соответственно. Они служат примером независимого управления и не являются обнаруженной конфигурацией целевом роутере.

У каждой секции есть выбор политики, применённый и предлагаемый VPN, результат применения, причина и время последнего переключения, тревога недоступности всех кандидатов. Общие сущности — автоматика, режим, диагностика, состояние служб и история. Handshake и счётчики трафика возвращают `unknown` с `supported=false`.

## Быстрая проверка

1. В `main` выберите vpn_b. Начальный режим **observe** сохраняет политику и меняет предлагаемый VPN, применённый остаётся vpn_a. Убедитесь, что другие секции не изменились.
2. Параметры интеграции → «Общие параметры» → **control**. Это включает применение только в симуляторе. Повторите выбор VPN и посмотрите применённое назначение.
3. Для автоматики выберите `main → Auto`, включите глобальный переключатель. Ручные секции остаются ручными.
4. Параметры → «Демонстрационные сценарии» → «vpn_a недоступен». Сценарий выполняет нужное число синтетических циклов отказа; main выбирает vpn_b. «Все VPN недоступны» сохраняет последнее назначение и устанавливает тревогу.
5. «Восстановить все VPN» возвращает доступность. Приоритетный VPN возвращается после удержания, по умолчанию 600 секунд. Для быстрой демонстрации временно задайте удержание 0 в общих параметрах.
6. Откройте сущность недавних событий, посмотрите атрибуты. История ограничена последними 20 событиями в HA; контроллер хранит 200.

Чтобы увидеть откат: восстановите все VPN, выключите автоматику, включите control, выберите main → vpn_a. Запустите сценарий **«Ошибка проверки следующего применения»**, затем выберите main → vpn_b. HA сообщит об ошибке применения, применённый VPN останется vpn_a, состояние будет «Выполнен откат», событие появится в истории. Повторное применение требует новой команды политики; фоновые циклы после отката его не повторяют.

Кандидаты и алгоритм меняются через параметры → «Политика секции». Кандидаты — имена через запятую в порядке приоритета; предпочтения — JSON вида `{"vpn_b": 3}`. Доступны priority/quality, after_hold/sticky, гистерезис и предпочтения. Режим наблюдения сохраняет назначения без сетевого применения.

## Хранение и жизненный цикл

Демонстрационный backend, TLS-сертификат и случайные RPC-реквизиты создаются в `.storage/openwrt_vpn_demo/<entry_id>/` конфигурационного каталога HA. В config entry хранится только флаг демонстрации и уникальный идентификатор; диагностика исключает секреты. Сервер слушает только `127.0.0.1` на свободном порту, клиент проверяет CA и hostname. После перезапуска порт может измениться, идентификаторы сущностей сохраняются.

Политики, назначения и история сохраняются. Искусственные отказы сценариев не сохраняются между перезапусками backend: после запуска проверки снова успешны. Удаление записи интеграции не используется как способ очистки демонстрационных файлов; для новой демонстрации создаётся новый entry_id.

При выгрузке интеграции закрываются сессия и HTTPS listener. При остановке HA останавливается демонстрационный цикл. **Эта встроенная демонстрация не работает при выключенном HA.** Будущий локальный OpenWrt Controller должен работать автономно, независимо от HA; это требование не изменено.

Тестовые сертификаты действуют 14 дней и пересоздаются при следующем запуске backend, если до истечения осталось меньше суток. Для длительного демонстрационного стенда перезагрузите запись интеграции до истечения сертификата. Открывать этот endpoint в LAN/WAN не требуется.

## Рабочее подключение и ограничения

Форма «Подключить контроллер по HTTPS» предусматривает endpoint, отдельного RPC-пользователя, пароль и CA PEM. Пустой CA использует системное хранилище доверия; TLS-проверку выключить нельзя. Для обычного OpenWrt ubus нужен отдельный нативный объект `vpn.controller` по [протоколу](protocol-prototype.ru.md).

Нативного ucode/procd-контроллера в этой версии нет. Шаблон rpcd ACL сам не создаёт объект и учётную запись. Реальные Podkop, sing-box, проверки ресурсов, egress и apply/rollback ещё не реализованы. IP демонстрации взяты из диапазона документации.

Capabilities: `simulated=true`, `production_control=false`, `safe_apply=false`, `fail_closed_verified=false`, `real_egress_verified=false`, `section_endpoints=false`. HA-команды доступны только симулятору. Реальная защита `inbound_vpn`, отсутствие утечек IPv4/IPv6 и конфликт с LuCI требуют испытаний на изолированном стенде. Не устанавливайте Python-симулятор на целевом роутере.

## Отдельный лабораторный сервер для разработки

Он нужен для тестов независимости контроллера от HA и клиентского транспорта. Для знакомства через HACS он не нужен.

```sh
cd /mnt/w/dev/hass-openwrt
bash tools/bootstrap.sh
bash tools/run_tests.sh
work/venv-linux/bin/python -m tools.demo
bash tools/run_lab.sh
```

Сервер: `https://127.0.0.1:8443/ubus`. CA: `work/lab/ca.pem`, реквизиты: `work/lab/credentials.json`. `tools.lab_control` управляет синтетическими отказами через отдельный lab_token. Приватные файлы исключены из Git и архивов. 127.0.0.1 у HAOS на другом компьютере означает сам HAOS, поэтому этот адрес не подключает HAOS к WSL.

Проверка выполняется с настоящим Core 2026.10.1. Совместимость с другими версиями и установка в HAOS пользователя пока не подтверждены. [Отчёт](prototype-validation.ru.md).

## Ошибки протокола

`operation.status`: completed, rolled_back, recovery_required, unknown. completed в observe подтверждает сохранение политики. После потерянного ответа клиент ищет исход по request_id и автоматически не повторяет запись. Конфликт revision требует свежего состояния и новой команды.

Сохраняются 256 операций и 200 событий. Старые request_id после выхода из окна хранения не повторять. Разрыв истории создаёт history_gap. При аварии между отправкой HA-события и записью курсора возможен повтор; для дедупликации используйте event_id.

Журнал операций обеспечивает смоделированный групповой откат и восстановление после рестарта. Конфликт/ошибка отката блокируют записи (recovery_required). Это поведение модели, а не доказательство безопасности реального Podkop.
