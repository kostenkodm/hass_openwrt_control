# Дополнение к ТЗ: транспорт Home Assistant → OpenWrt VPN Controller

Дата: 11 октября 2026. Статус: архитектурное решение до реализации.

Первоначального ТЗ и исходников контроллера в рабочей папке нет. Этот документ дополняет требования пользователя, не заменяет исходное ТЗ. Совместимость с конкретной версией OpenWrt/Podkop и измерения на роутере остаются этапом реализации. Настройки роутера не изменялись.

## 1. Решение

Основной путь: **Home Assistant → HTTPS с проверкой сервера → ubus JSON-RPC → локальный VPN Controller → UCI/Podkop**.

SSH остаётся установочным и явно включаемым резервным транспортом. Регулярные опрос и управление идут через специализированный объект `vpn.controller`. Отсутствие объекта или отказ ACL не должны незаметно включать SSH с более широкими правами.

Контроллер самостоятельно выбирает VPN, проверяет доступность, применяет политики и выполняет откат. HA служит клиентом состояния и намерений. Потеря HA, его перезапуск или истечение RPC-сессии не останавливают автоматику и не отменяют сохранённые ручные политики.

### Транспорт, авторизация и сессии

`Ubus` формирует JSON-RPC `call` с параметрами `[session_id, object, method, arguments]`, использует внешний aiohttp-клиент, поддерживает batch и таймаут. `session.login` получает токен и срок действия; `connect()` пытается уничтожить предыдущую сессию, `logout()` вызывает `session.destroy`. Есть блокировка повторного подключения — полезное решение для конкурентных опросов.

Недостатки, которые нельзя переносить:

- `_ensure_session_is_valid()` сравнивает срок с `time.time() - 15`: обновление происходит после истечения с запасом в неверную сторону. Нужен монотонный локальный deadline и обновление до истечения.
- Batch сопоставляет подсистему и метод через позицию `rpcs[i]`, хотя ответы JSON-RPC необходимо сопоставлять по уникальному `id`. Служебный ответ срока сессии тоже ищется как последний.
- `_batch_call()` изменяет переданный список, добавляя `session.list`; пустой batch не обработан. Не следует требовать чтения списка сессий при каждом опросе.
- Повторяется весь HTTP-запрос при ошибке соединения, без разделения чтения и изменения. Для записи потеря ответа означает неизвестный результат, а не гарантированный отказ.
- HTTP-код, отличный от 200, превращается в `None`; `[0]` также даёт `None`. Транспортная ошибка и успешный ответ без данных становятся неразличимы.
- Ошибки JSON-RPC и ubus разделяются частично; permission denied нельзя автоматически считать истечением сессии. Нужны типизированные ошибки и ограниченное восстановление.
- В логах присутствуют идентификаторы сессий; debug печатает параметры вызовов, включая параметры login. Токены, пароли и конфигурационные секреты необходимо редактировать до логирования.
- HTTPS и проверка сертификата в настройках по умолчанию отключены. Для нового клиента это недопустимый профиль.

### UCI и сервисы HA

`uci_get_option()` вызывает `uci.get`, передавая config/section/option. Однако HA-обработчик `uci_get` повторно ожидает оболочку `result`, уже снятую транспортом. Извлечение значения ненадёжно; контракт ответа следует проверять отдельно для чтения пакета, секции и опции.

`uci_set_option()` передаёт `values: {option: value}`, в том числе JSON-массив для UCI list. `uci_commit_config()` отдельно вызывает `uci.commit`. HA-сервис `uci_set_commit` последовательно выполняет set, commit, затем произвольный список restart. Он не реализует снимок, проверку фактического применения, блокировку конкурирующих изменений или откат; ошибки restart только журналируются. Его нельзя считать транзакцией.

HA-обработчики выбирают первый `data_manager_*`, а не явный роутер. При нескольких config entries команда может уйти не туда. Новый клиент должен адресовать конкретный config entry и сверять `controller_id`.

### Управление procd

Референс объединяет `rc.list`, `service.list` и batch запросов статуса. Изменения идут через `rc.init` с name/action; это отличается от чтения состояния procd. Неизвестные ответы местами превращаются в `running=false`, `enabled=false`, что скрывает недоступность. Новая интеграция получает только состояние контроллера и управляемых им компонентов. Общего `service_action(name, action)` в публичном API не будет.

### SharedUbusDataManager

Полезны общий HTTP-клиент, кеш с разными интервалами, блокировки по типу данных и DataUpdateCoordinator. Но возврат старого кеша при ошибке не маркируется как устаревший. Нужны `observed_at`, возраст, доступность и причина ошибки. Создание клиента также следует защищать блокировкой: текущая проверка наличия перед await допускает одновременное создание нескольких клиентов. Менеджер, кеш и RPC-сессия изолируются на config entry; часы TTL — монотонные. После записи кеш инвалидируется и перечитывается.

### Разрешения

README предлагает как wildcard ACL, так и расширенную ACL с общими системными объектами, `rc.init` и `file.exec` для определённой утилиты. Ни один профиль не подходит VPN Controller. Переиспользовать архитектурные идеи, не универсальные полномочия. При копировании кода отдельно проверить обязательства GPL-3.0; предпочтительно реализовать собственный узкий клиент.

## 3. Сравнение транспорта до реализации

| Критерий | SSH | HTTPS ubus JSON-RPC |
|---|---|---|
| Подлинность сервера | Проверка закреплённого host key | Проверка цепочки CA и имени сервера |
| Ограничение прав | Отдельный пользователь и forced command; обычный shell слишком широк | Отдельный rpcd login и ACL на конкретные методы; необходима валидация внутри метода |
| Задержки | Persistent SSH уменьшает handshake; запуск команд и разбор вывода дают накладные расходы | Keep-alive, структурированный ответ и агрегированный snapshot уменьшают число обменов |
| Сопровождение | Установка удобна; команды зависят от окружения и quoting | Версионированный контракт, схемы и типизированные ошибки; требуется установка RPC-плагина |
| Фактически доступные операции | Локальные UCI, службы и диагностика доступны установленному контроллеру | Референс демонстрирует `uci.get/set/commit`, `rc.init`, `service.list`; доменный API контроллера нужно реализовать |
| Транзакции и автономность | Обеспечивает локальный контроллер | Обеспечивает тот же локальный контроллер |

Выбор ubus обоснован наличием структурированного API и ограничением разрешений по методам. Преимущество в миллисекундах пока не измерено. Ни один транспорт сам по себе не обеспечивает транзакционность. На целевой системе проверить `ubus -v list`, пакеты rpcd/uhttpd, backend плагина и установленную версию Podkop; отсутствие универсального UCI-доступа у HA не препятствует локальному контроллеру работать с UCI.

## 4. Специализированный контракт v1

Объект `vpn.controller`; все параметры проходят строгую схему, неизвестные поля отклоняются. Идентификаторы секций стабильные, не индексы `@section[n]`; VPN выбирается из локального разрешённого реестра. Произвольные config, option, path, command, service и URL не принимаются.

| Метод | Назначение и параметры |
|---|---|
| `capabilities` | api_version, controller_id, поддерживаемые функции и ограничения |
| `status` | Снимок VPN, автоматики, применённых политик, проверок выхода, revision и незавершённой операции |
| `sections` | Разрешённые секции Podkop, stable id, режим, назначенный и фактический VPN |
| `set_automation` | enabled, явно заданная область: controller либо section_id; expected_revision, request_id |
| `assign_vpn` | section_id, vpn_id, mode=manual/auto; expected_revision, request_id. В auto vpn_id не задаётся |
| `diagnose` | section_id либо vpn_id, фиксированный профиль диагностики, request_id; возвращает operation_id |
| `operation` | operation_id: queued/running/succeeded/rolled_back/failed/recovery_required и безопасная причина |
| `history` | cursor, ограниченный limit, необязательный section_id; без секретов |

Пример запроса:

```json
{"jsonrpc":"2.0","id":"ha-42","method":"call","params":["SESSION_TOKEN","vpn.controller","assign_vpn",{"section_id":"work","vpn_id":"vpn_eu","mode":"manual","expected_revision":17,"request_id":"21b06c79-01e4-47ac-a2dc-1b6c640849c2"}]}
```

ubus success `[0, payload]` означает корректное выполнение RPC. При длительном изменении payload содержит operation_id, а не утверждение, что VPN уже работает. Итог определяется `operation` и свежим `status`. Разделить HTTP/TLS, JSON-RPC, ubus и доменные ошибки (`invalid_argument`, `protected_resource`, `revision_conflict`, `busy`, `verification_failed`, `rollback_failed`).

Для мутаций хранить request_id и хеш параметров: повтор возвращает ту же операцию, повтор с другими параметрами отклоняется. Дедупликация и журнал переживают перезапуск; срок хранения задаётся контрактом. После неизвестного результата клиент запрашивает операцию, а не генерирует новую команду. Чтение повторяется с ограниченным backoff/jitter; ошибки схемы, TLS и ACL автоматически не повторяются.

## 5. Учётная запись, ACL и TLS

Создать отдельный rpcd login `ha_vpn`, без интерактивного shell и root-пароля. Привязать только группу `ha-vpn-controller`, без `*`, `root` и наследуемых широких разрешений. Хеш пароля хранить в конфигурации rpcd с ограниченным доступом; пароль и токен не отдавать в диагностику HA.

Проект ACL `/usr/share/rpcd/acl.d/ha-vpn-controller.json`:

```json
{
  "ha-vpn-controller": {
    "description": "Home Assistant VPN Controller API only",
    "read": {
      "ubus": {
        "vpn.controller": ["capabilities", "status", "sections", "operation", "history"]
      }
    },
    "write": {
      "ubus": {
        "vpn.controller": ["set_automation", "assign_vpn", "diagnose"]
      }
    }
  }
}
```

Это проект, не установленная ACL. На выбранной версии rpcd проверить bootstrap `session.login`, уничтожение собственной сессии и отсутствие доступа к чужим сессиям. Если нужны дополнительные разрешения сессии, добавить только доказанно необходимые; не копировать `session.list` из референса. Проверять эффективные разрешения авторизованной сессии, а не только содержимое JSON.

Запретить HA вызовы `uci.*`, `file.*`, `rc.*`, `service.*`, системный reboot и `network.interface.*`. Внутренние полномочия локального контроллера не передаются удалённой учётной записи. ACL не ограничивает значения аргументов: защита секций, VPN и диагностических профилей обязательна внутри контроллера.

HTTPS обязателен. Проверять CA и hostname/SAN; частный CA явно доверяется в клиенте. Не использовать verify=false и автоматический переход на HTTP. Ограничить endpoint управления LAN/management VLAN либо доверенным VPN, разрешить firewall только адрес HA. Не слушать и не перенаправлять ubus с WAN, включая IPv6; проверить также существующие правила NAT и другие HTTP-listener. Ограничить размер запроса, число операций и частоту login/diagnose.

## 6. Локальная автономность и транзакционный откат

Все политики и ручные назначения сохраняются на OpenWrt. Ручной режим секции не отменяется отсутствием HA или очередным циклом выбора VPN. Семантика выключения глобальной автоматики — приостановить автоматические назначения, сохранив политики секций; явное возвращение в auto требуется отдельно. При восстановлении HA сначала читает состояние, не применяет старый локальный кеш.

`inbound_vpn` — защищённый ресурс: запрет изменения конфигурации, остановки, перезапуска, включения в пул автоматического выбора и побочного изменения маршрутов/правил, от которых он зависит. Проверять косвенные зависимости перед применением. Диагностика его доступности допустима только без изменений. Если исходное ТЗ задаёт более строгую защиту, действует она.

Изменение секции не должно перезаписывать соседние секции. Для общего файла UCI нужен общий lock записи плюс expected_revision; обновлять только разрешённые поля. Не коммитить чужие staged changes, не делать безусловный restore всего пакета поверх внешних правок.

Транзакция контроллера: валидация → запись устойчивого журнала намерения и снимка затрагиваемых данных → staging → применение совместимым с Podkop способом → проверка реального трафика → фиксация успеха. Проверять выход именно по маршруту/политике целевой секции: tunnel-up, handshake и ping с роутера недостаточны. Контрольный трафик должен учитывать routing/marks, DNS и поддерживаемые IPv4/IPv6; подтверждать выход через выбранный VPN и отсутствие запрещённого обхода.

При ошибке или локальном deadline выполнить восстановление конфигурации и runtime, затем проверить результат. Успех rollback не объявлять до проверки. При ошибке восстановления отметить recovery_required, прекратить дальнейшие конфликтующие изменения и сохранить диагностические данные. После сбоя питания/перезапуска локально восстановить незавершённую транзакцию по журналу. HTTP-соединение и доступность HA для отката не нужны. UCI commit сам по себе не является атомарной транзакцией нескольких пакетов и runtime.

## 7. Проверки перед принятием реализации

1. Инвентаризировать реальные версии OpenWrt/Podkop и ubus API; проверить формат UCI list, reload и поведение общих ресурсов Podkop.
2. Проверить TLS: доверенный сертификат работает; неверное имя, недоверенный/просроченный сертификат отклоняются без fallback. WAN IPv4/IPv6 недоступен.
3. От учётной записи HA проверить разрешённые методы и отказ всех универсальных объектов, неизвестных аргументов, чужих секций и косвенных изменений inbound_vpn.
4. Проверить два роутера, конкурентные записи, просроченную сессию, перезапуск rpcd, ответы batch в другом порядке и устаревший кеш.
5. Оборвать ответ после записи, повторить request_id; действие выполняется один раз. Проверить сбой после каждого этапа транзакции, перезапуск и неуспешный rollback.
6. Отключить HA: автоматический выбор работает, ручные назначения переживают перезапуск, соседние секции и inbound_vpn сохраняются. Воспроизвести ложный tunnel-up без рабочего выхода и убедиться в откате.
7. Измерить одинаковые status/assign операции через HTTPS keep-alive и persistent SSH: p50/p95, число обменов, CPU/RAM роутера и HA, восстановление после разрыва. Отдельно измерять транспорт и длительность VPN-проверки. Численные обещания до измерения не давать.

Остальные требования первоначального ТЗ сохраняются без изменений. До написания адаптера необходимы исходное ТЗ, код контроллера и сведения о целевой системе; этот анализ не утверждает проверку на физическом роутере.
